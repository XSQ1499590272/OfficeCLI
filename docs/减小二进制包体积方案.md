# OfficeCLI 减小二进制包体积方案

日期：2026-07-10  
作者：xiesq  
范围：Self-Contained 单文件发布包（以 `osx-arm64` 实测为准，其他 RID 预期同量级）

## 1. 目标

在**不影响 Office 文档操作功能**（Word / Excel / PowerPoint 的增删改查、`view` / `screenshot` / `watch` 等）的前提下，减小发布二进制体积。

约束：

- 保持 Self-Contained 单文件分发模型（用户无需预装 .NET）
- 不替换 `DocumentFormat.OpenXml`
- 不拆分 Word / Excel / PPT 为多个独立包（除非后续单独决策）
- 启动变慢需可量化、可接受

## 2. 现状与体积构成

### 2.1 发布配置（优化前）

`src/officecli/officecli.csproj` 已具备：

- `PublishSingleFile=true`
- `SelfContained=true`
- `PublishTrimmed=true`

优化前**未开启**单文件程序集压缩，`osx-arm64` 单文件约 **32MB**。

### 2.2 未打成单文件时的主要构成（约 40MB 目录）

| 部分 | 约大小 | 说明 |
|------|--------|------|
| `officecli.dll` | 8.0 MB | 业务 IL + 嵌入资源（skills / schemas / preview 等） |
| `DocumentFormat.OpenXml*.dll` | ~6.1 MB | Office 操作核心依赖，功能硬成本 |
| `libcoreclr` + JIT 等原生运行时 | ~15+ MB | Self-Contained 必然携带 |
| 嵌入 `skills/` | ~1.8 MB | 含 md / sh / pptx 样例等 |
| `schemas/help` | ~1.1 MB | `officecli help` 用，不影响文档读写本身 |

结论：体积大头是 **.NET 运行时 + OpenXml + 自有程序集**，不是某一条业务命令路径。

## 3. 推荐方案：开启单文件压缩（已落地）

### 3.1 机制说明

属性：`EnableCompressionInSingleFile=true`

含义：

- 发布时把打进单文件的**托管程序集**先压缩再打包
- 运行时由宿主**自动**解压到当前进程内存再加载
- **业务代码无需改动**；Office 操作逻辑不变

行为要点：

- 完全自动，无需手动触发解压
- **每个新进程启动**都会对压缩托管程序集做一次内存解压（不是“解压一次永久常驻”）
- 仅适用于 Self-Contained 单文件；Framework-Dependent 不能开（会报 `NETSDK1176`）

### 3.2 配置变更

在 `src/officecli/officecli.csproj` 中增加：

```xml
<EnableCompressionInSingleFile>true</EnableCompressionInSingleFile>
```

使用官方 .NET SDK 执行 `./build.sh release` 后，`bin/release/officecli-mac-arm64` 约为 **17MB**。

### 3.3 发布制品可移植性边界

`EnableCompressionInSingleFile` 不会自动引入 Homebrew Brotli；真正的风险是发布时采用了带构建机私有动态依赖的 host。例如 Homebrew .NET 的 macOS `singlefilehost` 可能引用 `/opt/homebrew/**`，即使关闭单文件压缩也会保留该依赖。

因此发布要求是：

- macOS 正式制品必须来自 CI 当前锁定的官方 .NET SDK `10.0.301`，并通过 `build/verify-macos-portability.sh`；只允许 `/System/Library/**` 与 `/usr/lib/**`。
- Windows 正式制品必须通过 `build/verify-windows-portability.ps1`；只允许已审计的 Windows 系统 DLL 与 `api-ms-win-*` / `ext-ms-win-*` API Set。
- 两个平台都在签名前和最终上传前复验；门禁只读，不通过改写依赖路径自愈。
- 本地 Homebrew SDK 可用于开发；若 release 门禁失败，应改用官方 SDK/CI，不得把失败制品用于分发。

## 4. 前后对比结论（实测）

测试环境：macOS arm64，.NET 10，Release，`osx-arm64` RID。  
对比二进制：

- 未压缩：约 **31.50 MB**
- 压缩后：约 **16.85 MB**

### 4.1 体积

| 指标 | 未压缩 | 压缩后 | 变化 |
|------|--------|--------|------|
| 单文件大小 | 31.5 MB | 16.9 MB | **-46%（约减半）** |

### 4.2 热启动（日常 CLI 更接近此场景）

命令：`officecli --help`，各 30 次：

| 指标 | 未压缩 | 压缩后 | 差值 |
|------|--------|--------|------|
| median | 125.1 ms | 144.0 ms | **+18.9 ms** |
| mean | 125.0 ms | 142.9 ms | **+17.9 ms** |
| min | 123.2 ms | 133.5 ms | +10.3 ms |

稍重路径 `officecli help`（各 15 次）median：124.7 ms → 137.9 ms，约 **+13 ms**。

### 4.3 冷启动近似

每次拷贝到新路径再启动（各 15 次）时，压缩版 median 反而更快（约 529 ms → 455 ms）。  
可能原因：二进制更小、读盘更省，盖过了解压开销。日常交互更应参考热启动数据。

### 4.4 综合结论

| 维度 | 结论 |
|------|------|
| 体积收益 | 显著：约 32MB → 17MB |
| 功能影响 | Office 业务逻辑无变化；发布可移植性必须独立验收 |
| 启动代价 | 热启动约慢 **15–20 ms**，对 CLI 体感通常可忽略 |
| 是否推荐默认开启 | **是**（已作为当前默认发布配置） |

## 5. 后续可选优化（按优先级）

以下均**未默认开启**；需单独评估后再做。

### 5.1 低风险、小幅收益（约再减 0.5–1MB）

可考虑关闭未使用的运行时能力，例如：

- `DebuggerSupport=false`
- `EventSourceSupport=false`
- `MetadataUpdaterSupport=false`
- `StackTraceSupport=false`
- `HttpActivityPropagationSupport=false`

实测：压缩基础上再开上述开关，约 **16.9MB → 16.2MB**。

**慎用** `InvariantGlobalization=true`：启动时会读取 `CultureInfo.CurrentCulture` 做字体 locale（`LocaleFontRegistry`），可能影响按系统语言选字体。

### 5.2 分发层压缩（减下载体积，不减解压后体积）

发布 `.tar.gz` / `.zip`：下载更小，解压后仍是完整可执行文件。不影响功能，适合 npm / GitHub Release 分发。

### 5.3 嵌入资源裁剪（收益有限，需产品决策）

- 不嵌入 morph-ppt 的 `.pptx` / `.sh`：对文档读写无影响，但可能影响内置 skill 安装完整性；压缩后收益仅约数百 KB
- 压缩 help schema / 外置 skill：改变安装与 help 行为，需单独方案

### 5.4 高风险 / 改变分发模型（暂不推荐作为下一步）

| 方向 | 潜在收益 | 风险 |
|------|----------|------|
| Native AOT | 可能再缩小 | OpenXml / 反射 / trim 回归成本高 |
| Framework-Dependent | 体积可到很小 | 要求本机已装 .NET，改变分发承诺 |
| 替换或裁剪 OpenXml | 理论可减数 MB | 直接威胁 Office 操作正确性 |
| 按 Word/Excel/PPT 拆包 | 单包可变小 | 安装与命令面复杂化 |

## 6. 明确非目标

- 不为瘦身重做渲染架构
- 不破坏公开 CLI / SDK / 安装 / skill 入口
- 不以牺牲 Office 操作正确性换体积
- 不把仓库文档/examples 清理与发布二进制瘦身混为一谈（仓库维护见 `docs/superpowers/specs/2026-07-08-officecli-slimming-design.md`）

## 7. 验证建议

开启或调整发布开关后，至少验证：

1. 使用官方 .NET SDK 执行 release publish，记录 `command -v dotnet` / `dotnet --info`
2. macOS 执行 `build/verify-macos-portability.sh <binary>`
3. Windows 执行 `build/verify-windows-portability.ps1 <binary>`
4. 确认体积量级（osx-arm64 约 17MB）
5. 冒烟：`officecli --help`、`officecli help`
6. Word / Excel / PPT：创建或修改 → `view html` → `view screenshot`
7. CI 跨平台 publish / smoke，并在最终上传前重新执行可移植性门禁
8. 可选：热启动前后对比（`time` 或脚本多次取 median）
