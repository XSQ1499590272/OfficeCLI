# OfficeCLI 功能收缩与主干收敛分析

> 状态：第一阶段已实施（2026-07-11）。
>
> 本轮已删除插件生态、CLI 自安装、后台更新检查和 `skills install`；保留 MCP stdio、MCP 注册/注销与只读 `load_skill`。
>
> 判断基准：先定义产品不可替代的目标，再判断某项能力是否属于主链，而不是仅按代码量、测试数量或“功能很少被用到”的直觉删除。

## 1. 产品目标与主干边界

OfficeCLI 的不可替代价值是：以稳定、可脚本化的方式读取、查询、修改、验证并保存 `.docx`、`.xlsx`、`.pptx` 文件。

因此，最小闭环是：

```text
CLI / MCP stdio
  -> 命令参数与 JSON 契约
  -> DocumentHandlerFactory
  -> Word / Excel / PowerPoint handler
  -> OpenXML 包读写
  -> validate / save
```

主干命令应包括：

- 创建与读取：`create`、`get`、`query`
- 结构化编辑：`add`、`set`、`remove`、`move`、`swap`
- 多步操作与安全边界：`batch`、`validate`、`save`
- 完整性与可演进性：`help`、`raw`、`raw-set`、`add-part`、`dump`

其中 `raw/raw-set/add-part` 不是常规路径，却是未被高层命令覆盖时的通用回退通道；`dump` 是 round-trip/迁移能力。它们不应因为“低频”而被删除。

## 2. 当前功能分层

| 层级 | 能力 | 是否主干 | 结论 |
|---|---|---:|---|
| 文档引擎 | 三种格式 handler、结构化读写、验证、批处理 | 是 | 保留 |
| 兼容性回退 | raw、raw-set、add-part、dump | 是 | 保留 |
| Agent 接入 | MCP stdio 服务、JSON 输出 | 取决于产品定位 | 对嵌入式 Agent 使用场景应保留纯 stdio 服务 |
| 运行加速 | resident 的 `open/close/save` | 否 | 有价值，但可由无状态命令和 `batch` 替代 |
| 实时可视化 | `watch/unwatch`、mark/unmark/marks/goto、SSE 预览 | 否 | 完整的外围子系统 |
| 视觉输出 | `view html/svg/screenshot/forms` | 否 | 可选验收体验，不等同于文本/结构检查 |
| 生态扩展 | plugins | 否 | 现有三格式能力不依赖它 |
| 安装分发 | install、MCP 注册、skills install、更新检查与 config | 否 | 与文档处理完全分离 |
| 创作增强 | Mermaid、动画、转场、3D 模型、模板 merge、CSV 导入 | 否 | 应逐项按产品方向决定 |

## 3. 第一批候选：可独立移除的外围模块

### 3.1 插件生态

范围：`plugins` 命令、`Core/Plugins/**`、插件协议与插件代理路径。

执行结果：已删除；由插件提供的额外格式和 PDF 导出也随之退出支持范围。

现状：插件用于把 OfficeCLI 扩展到额外格式或外部导出能力；内建的 Word、Excel、PowerPoint 三条处理链不依赖它。`Core/Plugins` 约 1,942 行，且拥有独立的发现、manifest、进程调用、schema lint 等生命周期。

建议：若近期没有“支持第四种文件格式”或插件生态计划，作为第一批删除对象。它能收缩边界，而不会降低三种主格式的编辑能力。

### 3.2 安装、更新与多客户端注册

范围：CLI `install`、`config`、后台更新检查、`skills install`。

执行结果：已删除；MCP stdio 与 `mcp <target>` 的注册/注销按本轮决策保留。

执行边界：外部发行脚本、npm 二进制下载器及 SDK 的二进制引导已一并删除；SDK 只接受 PATH 或显式二进制路径。

应保留的最小面：`officecli mcp` 的 stdio 服务本身。

原因：文档操作与嵌入式 MCP 只需要由宿主以绝对路径执行 `officecli mcp`。二进制自安装、扫描多个 AI 客户端目录、写入各客户端配置、后台自更新均不参与主流程，反而引入本机状态、网络和部署耦合。

注意：`McpServer` 不能和 `McpInstaller` 一并删除；前者是工具协议适配器，后者是本机配置写入器。

### 3.3 专项 Skills 的分发与内嵌资源

范围：`skills install`、`load_skill` 及专项 skill 包。

执行结果：已删除向外部 Agent 目录写入文件的 `skills install`；保留只读 `load_skill` 和内置 skill 资源。

现状：专项 Skills 及参考资源约 1.58 MiB，并通过项目文件嵌入发布二进制；它们用于引导 Agent 生成特定类型的文档，不参与 OpenXML 读写。

建议：如果产品定位是“文档引擎”，删除专项 skill 包和安装器，只保留 schema `help`；如果产品定位是“交付高质量 Office 成品的 Agent 工具包”，则保留。它是产品策略选择，不是实现正确性问题。

## 4. 第二批候选：有价值但架构成本较高的功能

### 4.1 Watch、批注和跳转

范围：`watch/unwatch`、`mark/unmark/marks/goto`、`Core/Watch/**`，以及 resident 中的 SSE 通知分支。

该子系统约 3,281 行，依赖 HTML 渲染、HTTP/SSE 服务、内存中的标注状态及 resident 通知。普通的一次性 `create/get/query/add/set/...` 不需要它。

建议：如果不做“浏览器中的实时协作式预览”，整块删除。删除时应同时移除隐藏的顶层兼容命令，避免留下无实现的历史入口。

### 4.2 Resident 常驻进程

范围：`open/close/save`、`ResidentServer`、`ResidentClient` 及各命令中的 `TryResident` 分支。

收益：减少跨进程重复打开文件的开销；为 Watch 提供实时刷新基础。

代价：状态、文件锁、自动 flush、并发和“外部程序何时能读取落盘文件”等语义渗透到大量命令。

结论：它不是文档引擎的逻辑必需品，因为无状态命令和 `batch` 已可完成闭环；但它是跨切面能力。应在删除 Watch 后，再决定是否将产品收束为无状态 CLI，不能把它作为一次小型清理。

### 4.3 视觉渲染与截图

`view` 应拆成两类：

- 应保留：`text`、`annotated`、`outline`、`stats`、`issues`。它们服务于结构检查与机器可读诊断。
- 可选：`html`、`svg`、`screenshot`、`pdf`、`forms`。它们服务于视觉验收、浏览器体验和截图导出。

渲染代码分散在三种 handler、截图/PDF 后端和图表 SVG 渲染中；图表核心同时承担图表读写，不能按目录整体删除。若选择删除，只裁视觉输出路径，不能误删 Chart 的结构化编辑能力。

## 5. 第三批候选：按格式的高级创作能力

| 能力 | 价值判断 | 建议 |
|---|---|---|
| PPT 动画与转场 | 对基础演示文稿编辑非必需，源文件约 156 KiB | 若定位为通用 Office 编辑器，可后续删除 |
| 3D 模型 | 低频创作特性；实现约 36 KiB，示例成品约 32.8 MiB | 高优先级的可选裁剪项 |
| Mermaid 图表 | 对 Agent 自动生成图表有价值，但不是文件编辑必需 | 面向 Agent 创作保留；纯编辑器可删 |
| 模板 merge | 专项但常见的文档自动化需求 | 不建议第一批删除 |
| CSV/TSV import | Excel 便利命令，可由 `batch` 替代 | 若要极简命令面，可后续讨论 |
| refresh | 仅 Windows + Word 的字段刷新 | 非主干但代码面小，优先级低于生态和 Watch |
| OLE/ActiveX 等复杂载体 | 实现跨 handler 且与保真/round-trip 相关 | 不应作为早期删除目标 |

## 6. 推荐目标架构

推荐收敛到“面向 Agent 的文档引擎”，而不是纯安装器或全功能创作平台：

```text
保留：CLI 原子命令 + batch + validate + raw 回退 + schema help + MCP stdio
可选：resident、结构化/文本 view
删除：plugins、所有安装/更新与 skills 写入分发、watch/批注
后续决策：视觉渲染与 PPT 高级创作能力
```

此方案保留嵌入式 MCP 场景：宿主直接启动 `officecli mcp`，不依赖自安装或后台更新；显式 MCP 注册/注销仍作为兼容入口保留。

## 7. 建议执行顺序与验证

### 阶段 0：冻结目标

在动代码前明确以下选择：

1. 是否保留 MCP stdio；推荐保留。
2. 是否需要浏览器实时预览；若否，Watch 与批注整块删除。
3. 是否将产品定义为无状态 CLI；若是，随后删除 resident。
4. 是否把专项 Skills 当成产品能力，而非文档资产。

### 阶段 1：低耦合收缩

删除 plugins、安装/更新和 Skills 写入分发；保留 `officecli mcp` 的启动路径。

验证：

- `officecli --help` 不再暴露被删除的管理命令。
- `officecli mcp` 仍能建立 stdio 服务。
- `create/get/query/add/set/remove/move/swap/batch/validate` 回归通过。

### 阶段 2：实时能力收缩

删除 Watch、批注和对应 resident 通知；单独提交并验证无 Watch 场景。

验证：一次性命令和 `batch` 能对三种格式完成“创建 -> 编辑 -> 校验 -> 保存”的闭环。

### 阶段 3：状态模型决策

若确定无状态化，再移除 resident。此阶段必须逐个清理所有 `TryResident` 分支、文件锁与 flush 语义，并将文档和 MCP 契约收敛到“每次命令均落盘”。

### 阶段 4：格式高级能力

按实际产品方向裁剪 3D、动画/转场、Mermaid 与视觉渲染；每项单独提交、单独验证，避免把“功能收缩”变成不可定位的大规模回归。

## 8. 明确不建议早期删除的能力

- 三种格式的主 handler 与结构化编辑命令。
- `validate`。
- `raw/raw-set/add-part/dump`。
- schema `help`。
- 图表的核心读写逻辑。

这些能力共同保证“遇到复杂真实 Office 文件时，工具仍有可解释、可校验、可回退的路径”。
